# Authoring rubrics with an AI, without a developer

Written 2026-08-14.

Every rubric in the database so far was generated by an AI and merged into the
project by hand. That works exactly once per developer and not at all for a
professor. This document specifies the pipeline that replaces it: a professor
pastes a prompt into any chat assistant, pastes the JSON back into grader, and
gets a rubric — with no file downloads and no understanding of JSON required.

Schema: [rubric.schema.json](rubric.schema.json).

## What the existing rubrics revealed

Before designing anything, all 14 rubrics were queried. The house style is
completely uniform, and it is not what `src/types/rubric.ts` describes:

- **Always exactly four levels**, with fixed labels: `Little / No Effort`,
  `Lacking Key Aspects`, `Good with Minor Flaws`, `Professional / Mastery`.
- **`weight` is 1.0 on every criterion in the database.** It is dead. Relative
  importance is carried entirely by point values.
- **Level points are a fixed fraction of the criterion's maximum.** Two families
  are in use: `3 | 10 | 18 | 25` (12/40/72/100%) and a 30/55/80/100% family.
  These are precisely the `bandEdges` in `RubricSettings` — a designed feature
  that was never persisted, since every `settings` column is NULL.
- Criterion maxima are scaled so the top row sums to the assignment's points
  possible, which is where values like `6.7`, `13.3` and `25.4` come from.

## The consequence: authored rubrics carry no points

Every point value in the system is derivable:

```
points(criterion, level) = totalPoints
                         × share(criterion) / Σ shares
                         × (level === 3 ? 1 : bandEdges[level])
```

So the authoring schema contains **no point values at all**. A criterion carries
a `share` — a relative number, normalised at import — and four level
*descriptions*. Points are computed.

This is not tidiness. It removes the single largest source of unusable AI
output: an assistant asked to produce 28 point values that sum to 100 across
seven criteria will get it wrong, confidently, and the professor has no way to
tell. It also makes rescaling an assignment from 100 to 150 points a recompute
rather than a rubric rewrite, and makes `bandEdges` a real, editable property
instead of an intention frozen into 649 grade entries.

`weight` should be deprecated in the database rather than carried forward. It
has never held a value other than 1.0 and its meaning was never defined.

## The professor's flow

1. **Rubrics → New → Generate with AI.** A form collects the things only the
   professor knows: course and assignment, what the work is, student level
   (freshman / senior / graduate), total points, roughly how many criteria, and
   optionally an existing rubric to imitate.
2. **Copy the prompt.** The page renders the filled-in prompt with a copy
   button, including the schema and — if one was chosen — a real rubric from
   their library as a worked example. Nothing is sent anywhere by grader.
3. **Paste into any assistant.** ChatGPT, Claude, whatever the professor uses.
   No API key, no cost to the department, no data leaving their control beyond
   what they chose to paste.
4. **Paste the reply back** into a textarea and press Validate.
5. **Fix, or import.** On failure the page shows plain-language errors *and* a
   copyable repair message to paste back to the assistant. On success it renders
   the rubric as the grading grid it will become, with computed points, and
   offers Import.

Step 5 is the part that makes this usable. An assistant that produces slightly
wrong JSON is the normal case, not the exception, and a professor who has to
understand a validation error is a professor who stops using the feature.

**Paste, not file upload.** The existing importer takes a `.json` file
(`rubric-library.tsx`). Nobody downloads a file from a chat window. Keep file
import, but the textarea is the primary path.

## Validation rules

The schema catches shape. These are the rules that catch a *plausible* rubric
that would still break something:

**Errors**

- Fewer than 2 or more than 12 criteria. Beyond twelve a rubric cannot be used
  during a live critique.
- Not exactly 4 levels on some criterion — the grading grid is a fixed grid.
- Duplicate criterion names, which make grade entries ambiguous to read back.
- `bandEdges` not strictly increasing, or outside (0, 1).
- Level descriptions identical across two levels of the same criterion, which
  means the assistant padded rather than discriminated.
- Any `share` ≤ 0.

**Warnings — import proceeds, but say so**

- Unknown keys. Assistants love to add `"total_points"`, `"instructions"`, or
  `"grading_scale"`. Strip them and report what was stripped; never fail on
  this, and never silently accept it either.
- A level description under ~40 characters, which is usually a stub.
- Shares that are all equal when the professor asked for weighting.
- Rubric name colliding with an existing rubric in the library.

**Deliberately not validated**

Whether the criteria are any *good*. That is the professor's judgement and the
preview grid exists so they can exercise it.

## The prompt

Rendered with the professor's inputs substituted. Kept in one place so it can be
improved as models change.

---

> You are helping a university studio-art professor write a grading rubric.
> Produce **only** a JSON document conforming to the schema below. No commentary
> before or after, no markdown fence, no explanation.
>
> **The assignment**
> - Course: `{{course code}} — {{course name}}`
> - Assignment: `{{assignment name}}`
> - What students produce: `{{description}}`
> - Student level: `{{freshman | sophomore | junior | senior | graduate}}`
> - Number of criteria: about `{{n}}`
>
> **Rules**
> - Do not include point values anywhere. Points are computed by the system from
>   each criterion's `share`. Use `share` to express relative importance: `2`
>   against two `1`s means that criterion is worth half the assignment.
> - Exactly four levels per criterion, ordered lowest to highest. Omit `label` —
>   the system supplies the standard labels.
> - Each level description says what the work **looks like** at that level, in
>   terms an instructor could point at on screen. Write about the artefact, not
>   the student: "Specular response reads as plastic on metal surfaces", not
>   "Student did not understand materials". Never write "Student shows effort".
> - The four descriptions for one criterion must be genuinely distinguishable.
>   If two levels could describe the same submission, rewrite them.
> - Criteria must be separately observable. If two criteria would always receive
>   the same score, merge them.
> - Pitch the vocabulary at the stated student level.
>
> **Schema**
> ```json
> {{contents of docs/rubric.schema.json}}
> ```
>
> **A rubric in this department's house style, for tone and grain:**
> ```json
> {{an existing rubric, exported}}
> ```

---

Two details in that prompt are doing real work. **"Write about the artefact, not
the student"** is what separates a rubric that survives a grade dispute from one
that reads as a personal judgement. **"If two levels could describe the same
submission, rewrite them"** attacks the most common failure in AI rubrics, which
is four paragraphs that are the same paragraph with intensifiers swapped.

The worked example matters more than any instruction. Offering a dropdown of the
professor's own existing rubrics as the style reference is the cheapest way to
get output in their voice, and it costs one `exportRubricToJSON` call.

## Round-tripping

`exportRubricToJSON` should emit this same v1 shape, so an existing rubric can
be pasted into an assistant with "revise the Lighting criterion for a graduate
seminar" and pasted straight back. Export currently emits the internal shape
with explicit points and dead weights; it should emit shares and no points, and
derive `bandEdges` from the stored levels.

That closes the loop: every rubric in the system becomes editable by
conversation, which is what a professor actually wants and what merging JSON
into a repository was standing in for.

## Points and calibration

The v1 band sets made it easy to fail students who were doing acceptable work.
This is the arithmetic, for four equally weighted criteria:

```
                          current 12/40/72   current 30/55/80   Advanced 55/74/88  Foundation 60/80/92
all mastery                       100.0% A           100.0% A           100.0% A            100.0% A
3 mastery, 1 good                  93.0% A            95.0% A            97.0% A             98.0% A
2 mastery, 2 good                  86.0% B           90.0% A-            94.0% A             96.0% A
all good, minor flaws             72.0% C-           80.0% B-            88.0% B+            92.0% A-
2 good, 2 lacking                  56.0% F           67.5% D+            81.0% B-             86.0% B
all lacking key aspects            40.0% F            55.0% F            74.0% C             80.0% B-
3 mastery, 1 no effort             78.0% C+           82.5% B-           88.8% B+            90.0% A-
2 lacking, 2 no effort             26.0% F           42.5% F             64.5% D             70.0% C-
all little/no effort               12.0% F            30.0% F            55.0% F              60.0% D
```

Read the fourth row. Work described as **"Good with Minor Flaws" in every
category earned a C−**. Work that was good in half the categories and lacking in
the other half failed outright. The bands were behaving correctly according to
numbers that disagreed with the words printed above them.

### Three causes

1. **Percentage-of-credit is not a quality scale.** Academic grading compresses
   everything usable into roughly 55–100; below 60 is one undifferentiated F.
   Spreading four quality levels evenly across 0–100 puts three of them at or
   below failing. Four levels have the top 45 points to work with, not 100.
2. **The labels promised what the numbers did not pay.** "Good with Minor Flaws"
   is a compliment; 72% is a C−. Grading happens with the words — you look at
   the work, decide it is good with minor flaws, and click — and the number then
   contradicts that judgement silently.
3. **Correlated criteria multiply one weakness.** Four criteria that all partly
   measure "was it lit competently" mark one lighting problem down four times.
   This is an authoring problem, which is why the prompt above says to merge
   criteria that would always receive the same score.

### The model

The rubric is dimensionless. The assignment supplies the points.

```
criterion %  = bandEdges[level]              (level 3 = 1.0)
rubric %     = Σ(share_i × pct_i) / Σ share_i
points       = round(rubric % × assignment.pointsPossible, 1)
```

**Round once, at the end.** Rounding per criterion and summing introduces drift,
and that is exactly where v1's `6.7`, `13.3` and `25.4` came from.

The payoff beyond calibration: one rubric works on a 50-point and a 200-point
assignment. That is what makes the linked-rubric model viable, since a child
course can change its assignment's points without diverging from the parent.

### Calibrate by letter grade

The professor sets each band by choosing **the grade that level deserves** from
a dropdown — A, A−, B+, B, B− — never by typing `0.72`. Three opaque decimals in
`settings.bandEdges` is precisely why this went wrong unnoticed.

Two presets, and the choice between them is a real pedagogical decision:

- **Advanced (55/74/88)** — for courses where "Professional / Mastery" is
  genuinely reachable, so B+ is the honest ceiling for good-but-flawed work.
- **Foundation (60/80/92)** — for courses where level 3 means professional and
  almost no student will reach it. Without this, a foundation class caps at B+
  no matter how well it is taught.

The question underneath: **is level 3 something a good student in this course
actually achieves?** If not, level 2 has to be worth an A−.

### Show the consequence while authoring

Render that table live in the rubric editor. "All level 2 → 88% (B+)", before
anyone has been graded. The v1 miscalibration was found by grading test students
and noticing they failed; nobody should have to discover it that way. Professors
calibrate from outcomes, not from reasoning about fractions.

### The nudge

Keep four descriptive states — they are the house style and they are good
feedback — and let the grader nudge a third of the way toward the neighbouring
band. That is ten effective values from four descriptions:

```
level                          minus      base      plus
Little / No Effort             48.7%     55.0%     61.3%
Lacking Key Aspects            67.7%     74.0%     78.7%
Good with Minor Flaws          83.3%     88.0%     92.0%
Professional / Mastery         96.0%    100.0%    100.0%
```

Level 0 has no band beneath it, so its downward nudge extrapolates the 0→1 gap
rather than inventing a floor. It never reaches zero — zero is what the
`missing` status is for.

Storage already supports this: `grade_entries` carries **both** `level_id` and
`score`. What the work *looks like* (the level, which is the feedback a student
reads) and what it *earns* (the number) are independent facts, and the schema
already treats them that way.

### A floor requires a companion change

A 55% floor is only defensible if **not submitting is a different state from
submitting poor work**. Otherwise it hands half credit to students who turned in
nothing, which is the standard objection to grade floors and it is correct.

`grades.status` gains `missing` — zero points, no levels selected, distinct from
"graded at level 0". With that, the floor stops being generosity and becomes
what it should be: recognition that submitted work has value. F still exists.

## Build order

1. The schema and this prompt. Done.
2. A pure `validateRubric(json)` module returning `{errors, warnings, normalised}`
   — no UI, fully unit-testable, unaffected by the in-flux grading UI.
3. `computePoints(rubric, totalPoints)` and its inverse for export.
4. The paste-and-validate page, with the repair message.
5. The generate-prompt page with the example dropdown.
6. Migrate `exportRubricToJSON` to v1 and deprecate `weight`.

Steps 2 and 3 are pure functions and can land now. Steps 4 and 5 touch rubric UI
that is still moving, so they should wait for it to settle.
